# 0013: Deterministic standalone Lenovo collection

Date: October 20, 2026. The owner requested code-driven collection and selected all visible account orders from the last 90 days.

Implement the first transport as a standalone Node 24/TypeScript CLI in `services/browser-runner`, with pinned Playwright and the already verified isolated VM browser environment. Its runtime uses fixed page/API paths, normal Lenovo SSO, explicit parsers and bounded validation. It has no language-model, agent, MCP or Windows browser dependency after initial session provisioning. Run once from operator-controlled private configuration; ongoing cadence remains unselected.

The observed order list supports pagination and period buckets. Traverse the complete visible list within explicit page/order limits, select 90 inclusive placement calendar dates in the configured timezone, fetch each selected order detail, then repeat the complete list traversal. Check page/totals/version/duplicate identities and compare membership/date/status across passes. Treat the result as coverage over a collection interval, not an atomic supplier snapshot. Source/customer identity is pinned to independently confirmed configuration; records cannot select the account.

Preserve the website's line/component/split hierarchy and separate shipment records. Read the structured order arrays, not recommendation DOM elements. Keep exact numeric IDs from the original JSON token so 64-bit item IDs are not rounded by JavaScript. Preserve decimal strings and unknown quantities. Shipment-level ETA and actual delivery dates remain separate. A human ETA without a year is stored as its label plus an unknown parsed date; a service's fulfilled label is not evidence of delivery. Carrier date semantics and missing source units remain explicit open mapping work.

This extraction document is `lenovo_orders.v1`, not a `domain.Batch`. The current Go line model cannot faithfully represent every observed shipment schedule and the required private connection/vault binding is not wired. Do not flatten multiple ETAs or send the document through fictional upload routes. Canonical mapping and a private application ingestion proof remain the next implementation step.

Keep keys, configuration, encrypted session state and encrypted captures outside the checkout. Reuse the sandboxed headed browser under Xvfb for normal renewal. Persist updated state only after validated collection. Use bounded transient read retries and one fresh collection attempt after normal authentication recovery; challenge, wrong-account and persistent schema failures require attention. The wrapper owns the execution lock, network-none container and exact-host public-IP proxy. API paths and the dictionary/renewal POSTs are reviewed allowlists; no arbitrary URL endpoint is exposed.

Each accepted run keeps an immutable encrypted observation and a comparison to the previous capture. An initial baseline invents no change event, and unchanged repeated facts create no duplicate changes. Unexplained loss of in-window orders, lines or shipment coverage prevents acceptance. Replace the accepted pointer atomically only after validation; a failure after the final filesystem rename requires inspecting that pointer. Failed collection cannot manufacture successful source freshness or shipment metrics in the application.

Owner-local evidence includes successful repeated code-only pulls, live multi-page traversal, forced client-cookie expiry/normal renewal, encrypted restart and deliberate limit failure preserving accepted data. Three consecutive final renewal trials passed. Exploratory startup runs also hit schema validation without accepting data; their cause was not reproduced or confirmed, so these checks do not establish long-term unattended reliability. Natural/multi-day expiry and interactive authentication remain separate gates. Tests use invented source shapes only. See BUILD_STATUS for executed checks and remaining skips.
